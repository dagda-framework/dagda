# M0 runtime prototype

This is the first implementation slice of Dagda, not the public framework API.
It exercises HTTP → bounded worker → parameterized PostgreSQL query → owned JSON
response. The integration, failure, and 30-minute stability checks described below
passed on 2026-11-06. The transport decision supports proceeding to M1 prototype
development within the current limits.

## Setup and checks

Supported target for this prototype: Linux x86_64. Odin's Linux `core:nbio`
requires a kernel supporting its io_uring flags and permission to create a ring.
Restricted containers and sandboxes may deny this operation.

Required tools: `bash`, `curl`, `tar`, `sha256sum`, Python 3, a C compiler, and
libpq 17 or newer (asynchronous cancellation API). Integration tests additionally
require `initdb`, `pg_ctl`, and `psql` in PATH. Run them as a regular user.

```sh
bash scripts/setup-odin.sh
./scripts/odin.sh version
./scripts/build.sh
./scripts/test-unit.sh
./scripts/test.sh
# Quick check of the optimized load harness, then the full 30-minute run:
./scripts/load-test.sh --duration 30 --warmup 5 --sample-interval 1
./scripts/load-test.sh
```

The installer verifies the archive SHA-256 from `dagda.lock` and installs inside
`.tools/`. It does not modify the system compiler or shell configuration.
An already-downloaded archive can be supplied as its first argument. The official
`dev-2026-11a` Linux archive reports `dev-2026-11-nightly:9a69916` internally.

`test-unit.sh` checks libpq connection-target parsing, JSON response framing, and
800 real worker-to-event-loop handoffs with expired jobs and repeated slot reuse.
`test.sh` builds the runtime, runs those unit tests,
creates a private temporary PostgreSQL cluster with a Unix socket and seed data,
then checks database responses, event-loop responsiveness, overload, deadlines,
cancellation, SQL errors, disconnected clients, malformed framing, slot reuse,
and SIGTERM drain with unfinished headers. It additionally terminates active
PostgreSQL backends, stops/restarts its cluster three times, sends malformed and
oversized headers/request lines, tests idle and trickling clients, and runs 160
disconnects/resets while checking descriptor and thread counts. Cleanup only targets processes and
the cluster created by that test. No existing database is used.

Test logs are retained under `build/runtime-checks/<timestamp>/`, while temporary
database storage is removed. The fixture clears inherited PostgreSQL environment
settings and disables `psqlrc` processing. `tests/support.py` owns setup/cleanup
for all suites. Test-fixture PostgreSQL runs with fsync disabled for speed; this
does not test durability or production database throughput.

Ctrl-C ends a run without qualifying it. Cleanup ignores repeated Ctrl-C while
stopping owned services; database storage is removed only after shutdown is
confirmed. If shutdown cannot be established, its directory is preserved and
reported. A completed load run has `result.json`; progress files alone do not
indicate a pass.

## Sustained load

`scripts/load-test.sh` compiles with `-o:speed`, retains debug information and
assertions, and runs a fixed-rate workload on the same machine as PostgreSQL:

- 30-second warmup, followed by 1,800 seconds of measurement.
- 40 total requests/second: half small JSON responses, half indexed PostgreSQL
  lookups alternating the two seeded rows.
- At most eight outstanding client requests; each opens a new HTTP connection.
- Server RSS, virtual memory, descriptor/thread counts, and admitted work sampled
  every five seconds. Warmup statistics are separate from measured statistics.

This is a repeatable stability workload, not a maximum-throughput benchmark. The
64-connection cap and 500 ms connection-close grace period constrain this prototype's
connection churn. Higher rates can hit that cap even when the database is idle.

The harness reports completed/successful throughput, response/transport errors,
generator drops, and p50/p95/p99 latency separately for JSON and database routes.
Latency uses bounded 1 ms histogram buckets. Scheduled latency includes client
scheduling delay; service latency starts when the client worker begins. A late
generator skips and counts missed requests instead of hiding them with catch-up
bursts. Reported resource usage covers the server process, excluding PostgreSQL
and the Python load generator.

Artifacts include `metadata.json` (machine, kernel, compiler, PostgreSQL, source
revision/dirty state, executable SHA-256, workload settings), per-phase resource
CSVs and histogram JSON, service logs, and `result.json`. `--output` chooses a new
artifact directory; existing directories are rejected to preserve previous runs.

The default gate requires no failed responses, client drops, or monitoring errors;
admission at most eight; stable thread count; descriptor median growth at most
four; RSS median growth at most 8 MiB between the first and last fifths; and a
late-half RSS slope at most 0.25 MiB/minute. These are explicit initial budgets,
not a claim that passing proves absence of leaks. Thresholds are configurable and
recorded. A shorter run is labeled a smoke test and defers the sustained-slope
check. Passing a smoke run does not satisfy the 30-minute requirement.

## Running manually

Create a disposable database and apply `tests/seed.sql` to it, then run:

```sh
DAGDA_DATABASE_URL='host=/run/postgresql dbname=dagda_m0' ./build/dagda-m0
curl http://127.0.0.1:8080/health/live
curl 'http://127.0.0.1:8080/items?id=1'
```

Adjust the socket directory and database name to your installation. Connection
settings use libpq conninfo syntax. One absolute Unix socket directory or
`hostaddr=127.0.0.1` / `hostaddr=::1` is required. Service lookup and inherited
`PGSERVICE`, `PGHOST`, and `PGHOSTADDR` overrides are rejected. This constraint
keeps DNS and remote connection behavior outside the initial proof.

| Variable | Default | Meaning |
| --- | --- | --- |
| `DAGDA_DATABASE_URL` | Required | Local PostgreSQL conninfo |
| `DAGDA_LISTEN` | `127.0.0.1:8080` | Numeric HTTP endpoint |
| `DAGDA_DEADLINE_MS` | `2000` | Queue + connect + query deadline, 50–30000 ms |
| `DAGDA_TEST_ROUTES` | Off | `1` enables slow-query, SQL-error, and pool-state fixtures |

## Ownership and budgets

The HTTP adapter uses one event loop. Admission reserves one of eight slots
before publishing work to two worker threads. Each worker exclusively owns one
libpq connection. SQL parameters are sent separately from query text.

A work item contains scalars copied from the parsed request. Its slot holds a
fixed 32 KiB arena for database result and response data. A prepared nbio
operation returns completion to the owning event loop; worker threads never
write HTTP response objects. The event loop copies response bytes into the
connection's arena before returning the slot to the free pool. Completed work
retains its admission slot until consumed, bounding outstanding completions too.

The ninth admitted database request receives 503 with `Retry-After: 1`. There
are at most 64 HTTP connections, 16 KiB of headers per request, a two-second
request-read timeout, and a one-second response-write timeout. Connection arenas
start at 64 KiB and can grow; this is not a hard total process-memory limit.
Responses close their connection. Body-consuming routes and keep-alive are not
part of this proof.

Deadline expiry initiates libpq asynchronous cancellation with a separate
100 ms cleanup budget, then discards the connection. Cancellation is best effort;
the integration test checks PostgreSQL actually stops the slow query locally.
Other query results are fully drained before connection reuse. Returned text is
copied before `PQclear`. SIGTERM stops accepts and drains admitted work; incomplete
requests and slow writes are bounded by transport timeouts.

## Dependencies and remaining gates

`dagda.lock` pins the compiler archive and upstream HTTP source revision.
`vendor/odin-http/DAGDA.md` records local transport changes. libpq is a system
library rather than a bundled or version-pinned release artifact. The small
POSIX shim provides signal handling, a monotonic clock, and socket polling.

Verified on 2026-11-06 with the pinned Odin compiler and PostgreSQL/libpq 18.6:
the compiler build, connection-validation test, and JSON-framing regression test
pass. A user-run terminal integration test passed all eight groups: database
responses, responsive event loop, bounded admission, query cancellation/recovery,
disconnected clients, malformed framing, repeated reuse, and graceful shutdown.
The original three unit tests also passed in the terminal with memory tracking enabled,
including 800 worker handoffs and slot reuse. Sandboxed runtime tests have been
denied io_uring setup and PostgreSQL socket binding.

Additional failure checks passed on 2026-11-06: backend termination, three database
outage/restart cycles, malformed names/control bytes/folding, oversized headers
and request lines, idle/trickling clients, and 160 disconnects/resets. The latter
retained eight descriptors and three threads; RSS went from 7,116 to 7,136 KiB.
The header-parser regression, four load-accounting/statistics tests, and three
fixture-cleanup regression tests also pass. The first sustained-load attempt
was interrupted after approximately 80 measured seconds, with no errors or RSS
growth observed up to that point; it does not satisfy the duration gate. The
subsequent smoke test and complete 30-minute run both passed.

### Recorded load result

See the [machine-readable validation summary](validation/2026-11-06.json) for the
workload, thresholds, machine details, executable fingerprint, and results. Raw
logs, histogram data, and CSV samples remain in the artifact directories recorded
there. The test used an Intel Core i7-1270P, Linux 7.2.15, PostgreSQL 18.6, and the
pinned Odin compiler, with the server and clients on the same machine.

| Measurement | Result |
| --- | --- |
| Measured duration | 1,800 seconds after 30-second warmup |
| Successful measured requests | 72,000 of 72,000 |
| Successful throughput at configured rate | 40 requests/second |
| Response/transport errors and generator drops | 0 |
| JSON latency p50 / p95 / p99 | 2 / 3 / 3 ms |
| Database lookup latency p50 / p95 / p99 | 3 / 4 / 5 ms |
| Early and late median server RSS | 6.496 MiB / 6.496 MiB |
| Peak server RSS | 6.500 MiB |
| Median descriptor growth | 0 |
| Server threads | 3 throughout |

Latency above includes generator scheduling delay and uses 1 ms bucket upper
bounds. Warmup added 1,200 successful requests excluded from the measured totals.
The server drained cleanly and the temporary database shut down after the run.

### Transport decision

Retain the pinned, patched `odin-http` transport behind the adapter for M1
prototype development, using the current connection, worker, arena, and timeout
budgets. The tested workload demonstrates stable resource use and recovery from
the exercised failures. It does not establish maximum capacity or production
readiness. Keep-alive, body-consuming routes, broader HTTP conformance, and
allocator/lifetime instrumentation remain separate gates before widening the
transport contract.

The checks led to fixes for invalid header names/control bytes, classification
of lost database connections as availability failures, and interrupted test
cleanup. Authentication/password hashing, transactions, migrations, durable
jobs, general routing, and the CLI are later milestones.
