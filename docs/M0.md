# M0 runtime prototype

This is the first implementation slice of Dagda, not the public framework API.
It exercises HTTP → bounded worker → parameterized PostgreSQL query → owned JSON
response. M0 remains open until its integration and memory/load gates pass.

## Setup and checks

Supported target for this prototype: Linux x86_64. Odin's Linux `core:nbio`
requires a kernel supporting its io_uring flags and permission to create a ring.
Restricted containers and sandboxes may deny this operation.

Required tools: `bash`, `curl`, `tar`, `sha256sum`, Python 3, a C compiler, and
libpq 17 or newer (asynchronous cancellation API). Integration tests additionally
require `initdb`, `pg_ctl`, and `psql` in PATH. Run them as a regular user.

```sh
bash scripts/setup-odin.sh
./scripts/odin.sh version
./scripts/build.sh
./scripts/test-unit.sh
./scripts/test.sh
```

The installer verifies the archive SHA-256 from `dagda.lock` and installs inside
`.tools/`. It does not modify the system compiler or shell configuration.
An already-downloaded archive can be supplied as its first argument. The official
`dev-2026-11a` Linux archive reports `dev-2026-11-nightly:9a69916` internally.

`test-unit.sh` checks libpq connection-target parsing, JSON response framing, and
800 real worker-to-event-loop handoffs with expired jobs and repeated slot reuse.
`test.sh` builds the runtime, runs those unit tests,
creates a private temporary PostgreSQL cluster with a Unix socket and seed data,
then checks database responses, event-loop responsiveness, overload, deadlines,
cancellation, SQL errors, disconnected clients, malformed framing, slot reuse,
and SIGTERM drain with unfinished headers. Cleanup only targets processes and
the cluster created by that test. No existing database is used.

## Running manually

Create a disposable database and apply `tests/seed.sql` to it, then run:

```sh
DAGDA_DATABASE_URL='host=/run/postgresql dbname=dagda_m0' ./build/dagda-m0
curl http://127.0.0.1:8080/health/live
curl 'http://127.0.0.1:8080/items?id=1'
```

Adjust the socket directory and database name to your installation. Connection
settings use libpq conninfo syntax. One absolute Unix socket directory or
`hostaddr=127.0.0.1` / `hostaddr=::1` is required. Service lookup and inherited
`PGSERVICE`, `PGHOST`, and `PGHOSTADDR` overrides are rejected. This constraint
keeps DNS and remote connection behavior outside the initial proof.

| Variable | Default | Meaning |
| --- | --- | --- |
| `DAGDA_DATABASE_URL` | Required | Local PostgreSQL conninfo |
| `DAGDA_LISTEN` | `127.0.0.1:8080` | Numeric HTTP endpoint |
| `DAGDA_DEADLINE_MS` | `2000` | Queue + connect + query deadline, 50–30000 ms |
| `DAGDA_TEST_ROUTES` | Off | `1` enables slow-query, SQL-error, and pool-state fixtures |

## Ownership and budgets

The HTTP adapter uses one event loop. Admission reserves one of eight slots
before publishing work to two worker threads. Each worker exclusively owns one
libpq connection. SQL parameters are sent separately from query text.

A work item contains scalars copied from the parsed request. Its slot holds a
fixed 32 KiB arena for database result and response data. A prepared nbio
operation returns completion to the owning event loop; worker threads never
write HTTP response objects. The event loop copies response bytes into the
connection's arena before returning the slot to the free pool. Completed work
retains its admission slot until consumed, bounding outstanding completions too.

The ninth admitted database request receives 503 with `Retry-After: 1`. There
are at most 64 HTTP connections, 16 KiB of headers per request, a two-second
request-read timeout, and a one-second response-write timeout. Connection arenas
start at 64 KiB and can grow; this is not a hard total process-memory limit.
Responses close their connection. Body-consuming routes and keep-alive are not
part of this proof.

Deadline expiry initiates libpq asynchronous cancellation with a separate
100 ms cleanup budget, then discards the connection. Cancellation is best effort;
the integration test checks PostgreSQL actually stops the slow query locally.
Other query results are fully drained before connection reuse. Returned text is
copied before `PQclear`. SIGTERM stops accepts and drains admitted work; incomplete
requests and slow writes are bounded by transport timeouts.

## Dependencies and remaining gates

`dagda.lock` pins the compiler archive and upstream HTTP source revision.
`vendor/odin-http/DAGDA.md` records local transport changes. libpq is a system
library rather than a bundled or version-pinned release artifact. The small
POSIX shim provides signal handling, a monotonic clock, and socket polling.

Verified on 2026-11-06 with the pinned Odin compiler and PostgreSQL/libpq 18.6:
the compiler build, connection-validation test, and JSON-framing regression test
pass. A user-run terminal integration test passed all eight groups: database
responses, responsive event loop, bounded admission, query cancellation/recovery,
disconnected clients, malformed framing, repeated reuse, and graceful shutdown.
All three unit tests also passed in the terminal with memory tracking enabled,
including 800 worker handoffs and slot reuse. Sandboxed runtime tests have been
denied io_uring setup and PostgreSQL socket binding.

Before accepting this transport: run broader allocator/lifetime checks,
sustained-load memory observation, latency/throughput measurements,
additional malformed-request tests, and lost-database-connection tests. No
production readiness or performance claim is made. The HTTP dependency remains
a prototype. Authentication/password hashing, transactions, migrations, durable
jobs, general routing, and the CLI are later milestones.
