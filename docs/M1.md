# M1: application foundation

The first two M1 tasks are implemented: configuration/lifecycle and routing/
middleware. The reusable packages are `dagda/config`, `dagda/app`, `dagda/http`,
and `dagda/routes`. `examples/api` demonstrates their use. These APIs are still
being developed. Typed JSON request/response support is now implemented as the
next slice; see [JSON.md](JSON.md) for its contract and verification status.
Explicit [field validation and structured errors](VALIDATION.md) are also
implemented; see that page for verification status. An [Odin application test
client](TESTING.md) and [common application errors](ERRORS.md) are now implemented
as well, with passing unit and integration checks. The [CLI skeleton](CLI.md)
now generates independent applications and implements doctor, build, and test.
The clean-generated-app acceptance gate passes: a copied CLI generates and builds
a release app, its request tests pass, and it serves typed JSON and validation
responses against an isolated PostgreSQL instance. The full regression run passed
38 Odin tests, 7 Python harness tests, and all six integration suites. See the
[CLI validation record](validation/2026-11-06-cli.json). M1 is complete for the
current Linux prototype scope; this is not production qualification.

## Run the example

```sh
./scripts/build.sh
DAGDA_DATABASE_URL='host=/run/postgresql dbname=dagda_m0' ./build/dagda-api
```

Apply `tests/seed.sql` to a disposable database first for the example's item
queries. The binary name is `dagda-api`; `dagda-m0` remains the original proof
fixture. Building requires the pinned compiler, C compiler, and libpq described
in [M0.md](M0.md).

```sh
curl http://127.0.0.1:8080/health/live
curl http://127.0.0.1:8080/health/ready
curl http://127.0.0.1:8080/items/1
curl http://127.0.0.1:8080/items/new
curl -H 'X-Demo-Key: example' http://127.0.0.1:8080/private
```

The demo-key middleware illustrates short-circuiting; it is not authentication.
The example's `POST /items` deliberately returns 501 until request bodies and
writes are implemented. Test-only slow-query/startup-failure fixtures are enabled
only with `DAGDA_ENV=test`.

## Configuration and lifecycle

Use `config.load()` for process environment settings, or `config.parse(Values{})`
for an explicit source. Both validate and return an owned `Config` plus a
field/message error. Error messages never echo connection strings or passwords.
Destroy the configuration after the application; `app.init` borrows it. Treat the
parsed configuration as immutable during the application's lifetime.

| Variable | Default | Accepted values |
| --- | --- | --- |
| `DAGDA_DATABASE_URL` | Required | One Unix socket directory or numeric loopback `hostaddr`; libpq conninfo |
| `DAGDA_ENV` | `development` | `development`, `test`, `production` |
| `DAGDA_LISTEN` | `127.0.0.1:8080` | Numeric IP endpoint |
| `DAGDA_DEADLINE_MS` | `2000` | 50–30000; database queue/connect/query budget |
| `DAGDA_READ_TIMEOUT_MS` | `2000` | 50–30000; absolute transport read budget |
| `DAGDA_WRITE_TIMEOUT_MS` | `1000` | 50–30000; response write budget |
| `DAGDA_MAX_CONNECTIONS` | `64` | 1–4096; the validated M0 default is 64 |
| `DAGDA_ACCESS_LOG` | `true` | `true`/`false`, or `1`/`0` |
| `DAGDA_LOG_LEVEL` | `warn` | `error`, `warn`, `info`, `debug`; transport diagnostics |

Inherited `PGSERVICE`, `PGHOST`, and `PGHOSTADDR` are rejected. Worker count,
admission capacity, and worker arena remain fixed at 2, 8, and 32 KiB. This slice
keeps the local database constraints of M0; it does not add remote TLS/service
configuration.

Lifecycle is `Configured → Starting → Running → Draining → Stopped`, with
`Failed` on startup/runtime errors. Registration freezes when startup begins.
Each `App` runs once; create another application instance for a subsequent run.
Only one application/event loop is supported per process at a time.

Startup performs a bounded database connection/query check, starts the workers,
runs the optional startup hook, and binds the listener. Failures return a nonzero
error to the executable. The example exits nonzero for invalid configuration,
unavailable database, hook failure, or occupied listener. No readiness is
advertised before startup completes.

`app.Hooks` accepts ordinary procedures with an explicit state pointer. The start
hook runs before listening. Its stop hook runs once after workers join, including
when the start hook returns false or a later bind fails. Hooks that were never
entered because an earlier startup stage failed do not receive cleanup calls.
Keep any hook-owned resources alive until that stop hook returns.

SIGINT/SIGTERM, or `app.request_stop` on the HTTP thread, enter drain. New accepts
stop; admitted work keeps its existing deadline and storage until completion.
Read/write timeouts also bound unfinished clients. Shutdown is cooperative and
cannot preempt arbitrary blocking application code; callbacks must return.

`GET /health/live` reports event-loop availability. `GET /health/ready` performs a
bounded query through the same admission/worker pool as application queries and
returns 503 on an outage, deadline, or saturation. It recovers on subsequent
successful probes. Schema compatibility checking will arrive with migrations in
M2; current readiness checks database connectivity only. Failed readiness uses the
common `not_ready` error envelope. Health routes are
reserved and use the same configured listener; production network exposure and
proxy access controls remain deployment responsibilities.

## Routing and middleware

Register routes using `app.route(application, method, pattern, handler, data,
middleware)`. Handlers receive `^http.Context`; route state is available as
`request.user_data`. Global middleware is added with `app.use`. Registered pattern
strings and middleware slices are copied into application-owned storage; caller
state pointers must outlive the application.

Patterns support literal segments and named parameters such as `/items/:id`.
Static segments take precedence at the first differing segment, independent of
registration order. Path selection precedes method selection: if a specific path
exists only for POST, GET returns 405 instead of falling back to a less-specific
parameter route. A 405 includes `Allow`. Unknown paths return 404. HEAD and
OPTIONS require explicit registration; HEAD responses omit body bytes while
preserving the intended content length. The transport still handles `OPTIONS *`.

Matching is case-sensitive and trailing slashes are significant. Paths are
percent-decoded exactly once. Malformed escapes, invalid UTF-8, encoded slashes,
backslashes, controls, dot segments, and repeated interior slashes are rejected.
Duplicate route shapes for a method and duplicate parameter names are startup
registration errors. Limits are 256 routes, 16 segments, and 8 named parameters.
There are no wildcards or regex routes in this slice.

Middleware runs in registration order: global middleware, route middleware, then
the handler. `http.next(next)` is synchronous and can be used once. Middleware
can short-circuit with a response. A handler that returns without responding or
scheduling database work gets a 500. Code after `next` runs as the synchronous
chain unwinds; an asynchronous database response may still be pending then.
Never retain `Next`, invoke it from a worker, or use it as an async continuation.

The request context, parameters, header/query views, and result strings are
request-owned. Do not retain them after response completion. Callbacks execute
on the HTTP loop and must not perform blocking I/O. Header lookup is case-insensitive;
response header setters reject protocol framing overrides and control bytes.

`http.query_text` schedules one parameterized SQL operation at a time. The pool
copies SQL and parameter bytes before returning; caller storage never crosses
into a worker. SQL is capped at 4 KiB, parameters at eight, and combined input at
8 KiB. Results remain capped at 8 KiB. Query text/result callbacks use the
request's original database deadline. Completion returns to the HTTP loop and
copies result bytes before releasing the worker slot. Further operations can be
scheduled from the result callback. There is no transaction API yet.

`http.json_text` accepts already-encoded JSON up to 8 KiB. `http.respond_json`
encodes typed responses, and `http.decode_json` decodes the bounded body into an
Odin destination. See [typed JSON](JSON.md) for supported types, framing, and
error behavior. Connections close after each response. A pending query cannot be
prematurely finalized by middleware, protecting the request's transport storage.

## Request IDs and access logs

Each accepted connection/request receives a generated UUID v4, returned as
`X-Request-ID` when a response is possible. Incoming request-ID headers do not
replace it. Transport observers cover parsed requests, parser rejections, and
incomplete/disconnected clients.

Access records are JSON lines on stdout, emitted once when response transmission
completes or the connection closes. Fields are `event`, `request_id`, `method`,
`route` (the registered template), `status`, `duration_ms`, and `outcome`.
Duration includes parsing/reading and sending. A client closed before a response
has status 0; failed sends are marked `write_failed`. No raw query strings,
parameters, headers, response bodies, or database credentials are logged.
Malformed transport diagnostics also omit raw request/header contents.

Lifecycle events go to stderr as JSON. Transport diagnostics use Odin's logger
at the configured severity. A custom synchronous `application.logger` can replace
the access sink; it must copy borrowed strings before retaining a record and
must avoid blocking the event loop.

## Verification

`./scripts/test.sh` builds both executables and runs unit tests, the existing M0
integration/failure suites, and `tests/application.py`. The M1 suite checks
configuration failures, route/method behavior, parameter decoding, middleware,
request IDs, repeated context reuse, readiness outage/recovery, log redaction,
startup hooks, listener conflicts, and drain with active queries/partial headers.
It creates and removes only its own temporary database. Artifacts are retained
under `build/runtime-checks/`.

Verification passed on November 6, 2026 (America/Chicago): 14 Odin unit tests,
7 Python harness tests, both M0 integration/failure suites, and the M1 application
suite. The application suite passed on a targeted rerun after fixing the Python
HEAD test's connection cleanup; no runtime changes were needed for that fix.
The run checked 144 response IDs against their access records. Across the
120-request reuse check, RSS stayed at 7096 KiB, with 3 threads and 8 descriptors
before and after. See the [validation record](validation/2026-11-06-m1.json).

The recorded 30-minute M0 result is historical evidence for that exact build;
it is not a performance claim for this expanded application layer.
